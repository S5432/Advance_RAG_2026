## Production questions

1. **Worker stopped during ingestion?** The document stays `PROCESSING` and the job row stops updating. Because the task
   uses `acks_late` and `reject_on_worker_lost`, the broker redelivers the message when a worker comes back (or another
   worker picks it up). Replay is safe: vector IDs are deterministic (upsert replaces) and chunk rows are deleted and
   re-inserted. With a graceful stop (SIGTERM) Celery finishes the current task first.
2. **Recover a stuck `PROCESSING` document?** The beat job `requeue_stuck_documents` runs every 10 minutes: any
   PENDING/PROCESSING document with `updated_at` older than 15 minutes gets a new job and task ID and is re-queued; if its
   source file is gone it is marked FAILED with a "re-upload" message. Manual path: re-upload the file (FAILED documents
   are re-queued) or call the task from a shell.
3. **Prevent duplicate Pinecone vectors?** Tenant-scoped content hash ⇒ the same file maps to the same `document_id`;
   chunk IDs are `{document_id}_chunk_{index}`; Pinecone upsert overwrites same IDs. If a changed document gets fewer
   chunks than before, delete stale IDs (`delete_ids`, using the chunk rows stored in PostgreSQL).
4. **A 500-page PDF?** Raise upload and time limits; stream-read the file; process in slices (already: 200 chunks
   per upsert step, with embeddings generated by Pinecone) with progress updates; OCR only pages without text and in parallel pages
   (Celery group/chord per page range); keep worker concurrency moderate (OCR and PDF parsing are CPU/RAM heavy; embedding is offloaded to Pinecone); use a
   dedicated "ingestion" queue so large jobs never delay small ones; watch Pinecone Inference rate limits and retry 429s (already handled by `PineconeService._retry`).
5. **Rate-limit users?** Per `tenant_id`/`user_id` token bucket in Redis (INCR + EXPIRE or a sliding window), enforced
   by a FastAPI dependency: e.g. 60 `/ask` per minute, 20 uploads per hour, return 429 with `Retry-After`.
   Add a global concurrent-stream cap per user, and Gemini-side quota backoff.
6. **Cache frequent questions?** Redis key = hash(tenant, normalised question, document filter, index version) →
   answer + citations, TTL ~1 h; invalidate by bumping the tenant's index version on every ingestion/delete. Never share
   cache entries across tenants. For streams, replay the cached answer as tokens.
7. **Protect confidential documents?** TLS everywhere; secrets in a secret manager; tenant filter enforced server-side
   and tenant derived from a verified JWT; per-document ACL metadata (`allowed_roles`) in the filter; encrypt uploads
   at rest and delete them after ingestion (done); don't log chunk text or questions; audit log; retention/delete
   endpoint removing vectors, chunk rows and files; check the LLM provider's data-handling terms.
8. **precision@5 / recall@5.** Build a labelled set: question → IDs of relevant chunks. Run `/search` with `top_k=5`.
   precision@5 = relevant in top 5 ÷ 5; recall@5 = relevant in top 5 ÷ all relevant. Average over questions; also
   track MRR and answer-level faithfulness. Re-run after every chunking/model change.
9. **Monitor Celery failures?** Flower dashboard; Prometheus exporter (celery-exporter) with alerts on failure rate,
   queue length and task latency; Sentry for exceptions; structured logs including `document_id` and `task_id`;
   alert on documents in FAILED, or PROCESSING beyond the threshold; the `ingestion_jobs` table is the audit trail.
10. **Deploy with Docker Compose?** `docker-compose.yml` runs `api`, `worker`, `beat`, `redis` (AOF persistence) and
    `postgres` (schema mounted from `migrations/`), health checks with `depends_on: service_healthy`, a shared
    `uploads` volume, secrets via `.env`. Scale workers with `docker compose up --scale worker=3`. Put Nginx/Traefik in
    front with TLS and `proxy_buffering off` for SSE; back up the Postgres volume.
